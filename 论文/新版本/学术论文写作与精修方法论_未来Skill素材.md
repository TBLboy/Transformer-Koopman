# 学术论文写作与精修方法论：从写作经验到可执行 Skill

> 用途：为后续编写论文写作/审稿/精修 `SKILL.md` 提供可复用的原则、工作流、检查清单与输出模板。适用重点：控制、机器人、机器学习交叉领域的数学建模与方法型论文。
>
> 来源区分：**[分享提炼]** 表示来自用户提供的公众号文章；**[项目经验]** 表示来自本次 Transformer–Koopman 论文多轮审阅的实际问题；**[综合规则]** 表示将二者转化为可执行写作规范。公众号文章是个人经验分享，不应视为所有顶刊的统一格式要求。

## 一、总纲：清楚、准确、必要、可核验

1. **先建立论证，再润色语言。** 先确定研究问题、证据、贡献与章节职责，后调整句式。好听的英文不能替代成立的逻辑。[综合规则]
2. **读者优先。** 每一段回答一个读者此刻最需要的问题；不要要求读者到后文寻找当前符号的基本定义。[综合规则]
3. **以信息密度而非字数衡量简洁。** 删除重复和空话，但不能删掉必要条件、定义、实验配置与复现细节。[综合规则]
4. **主张与证据同等级。** 设计选择、经验观察、实验比较、局部理论结果和严格保证必须分开表述。[项目经验]
5. **成稿阶段默认最小修改。** 保留已经正确的公式、标签、段落与章节接口；修改局部问题，不顺手重写整章。[项目经验]

## 二、吸收公众号文章的八个方法，但不机械套模板

| 公众号建议 [分享提炼] | 可以吸收的原则 | 必须避免的机械化理解 [综合规则] |
|---|---|---|
| 引言采用漏斗 | 从应用背景迅速收束到具体问题、研究缺口和本文工作 | 不能强制“四段”“前三句说完”；缺口必须有文献依据，不凭空声称无人研究 |
| 摘要按背景—问题—方法—结果—意义 | 摘要要形成完整研究闭环 | 不是必须五句话；未完成/未核验实验不能编造数字，方法论文可按期刊要求安排信息 |
| 方法像菜谱 | 关键流程、参数和条件应可复现 | 数学模型定义与代码级实现不应混写；理论定义先抽象，参数化和训练细节放适当位置 |
| 结果以图为主 | 正文强调图表支撑的关键发现，不逐项复述数据 | 图不能代替必要的数值、统计说明、对照设计和误差定义 |
| 讨论解释原因与局限 | 对比相关工作、分析可能机制、说明证据边界 | 不要把推测写成证明，也不要用“局限不影响结论”一笔带过实质缺陷 |
| 结论简短收束 | 只总结已证明/已观察到的贡献与适用范围 | 不强制三四句话；不得添加正文未支持的新结论 |
| 学习优秀论文句式 | 学习信息组织、逻辑连接与术语表达 | 不整句复制，不拼接现成句子；句式库应记录出处并进行原创重写 |
| 大量拆解论文 | 反向分析问题链、章节结构、图表和证据 | 数量不是目标；优先选本领域同类型、高质量、方法相近的论文 |

## 三、面向数学建模与控制论文的章节职责

### Abstract：研究闭环
- 问题是什么、为什么现有方法不足、提出了什么、得到了什么有证据的结果、意义何在。
- **禁令：** 无验证数据不写百分比、显著性或硬件实测结论；不把模型设计目标写成已实现的性能保证。

### Introduction：问题链与贡献定位
- 顺序建议：应用/任务 → 具体技术困难 → 现有方案的相关不足 → 本文解决路径 → 可核实贡献。
- 不把 Related Work 复制进引言；不为迎合自己的模块而人为制造研究缺口。
- 每个贡献应能指向正文中的公式、分析或实验。

### Related Work：按研究问题比较
- 按技术路线与研究问题组织，不做逐篇流水账。
- 对每类工作说明“解决了什么、在本问题下还差什么”；引用应真实支持具体判断。
- 避免“首次”“从未”之类无证据的排他性表述。

### Preliminaries / Problem Formulation：给定什么，求什么
- **Background** 只介绍后文必需的已有概念；**Problem Formulation** 明确系统、观测、历史、控制输入、预测输出、约束与目标。
- 公式首次出现时，必须定义对象、维度、作用和必要假设。
- 只出现一次、后文不用的抽象映射，优先改为直接的任务描述。
- 不把训练算法、RTI 求解细节和理论免责声明提前写进问题定义。

### Methodology：先模型，后训练，最后实现细节
- 推荐顺序：整体结构 → 核心映射/状态转移 → 递归预测 → 损失与训练流程 → 必要参数化与复现说明。
- 抽象数学定义要清楚：输入输出、依赖关系、约束、维度；具体网络层数/激活函数等可以在实现段落或实验设置中说明，但不能完全丢失关键可复现信息。
- 每个关键公式前一句说明它为什么出现，后一句解释其作用或变量；避免对公式逐符号重复讲解。
- 区分训练阶段、部署阶段以及每个阶段哪些参数更新、哪些状态重新编码。

### Theory：命题—假设—结论—适用范围
- 明确研究的是预测器自身的性质、与真实系统的误差，还是闭环控制性质；三者不可混同。
- 写清楚范数、光滑性、Lipschitz 条件、时域与局部/全局范围。
- 不用连续免责声明堆砌正文；在相关结论附近用最短必要限定交代边界。

### Control：从预测器到优化器的真实链条
- 明确预测状态、决策变量、代价、约束、线性化点、Jacobian 和求解器。
- 若声称 RTI-QP，必须确认实际代码求解的是线性化后的局部 QP，还是原非线性代价的有限次迭代；二者不可互换。
- 区分单次 RTI 外层线性化与内部 QP 求解迭代。

### Experiments / Results：图表回答主张
- 每个实验先写清“检验哪条主张”，再确定对照、数据、指标、统计和图表。
- 结果文字描述主要观察，讨论段再分析解释；不把未验证结果写进其他章节。
- 消融实验应尽量一次改变一个核心因素，并说明不能隔离的混杂因素。

### Discussion / Conclusion：收束而非扩张
- 讨论比较现有研究、解释观察、说明局限与适用范围。
- 结论只总结已支持的工作和结果，不引入新证据、未经证明的稳定性/鲁棒性保证。

## 四、我们修改 Transformer–Koopman 论文时发现的典型反例

### 反例 A：防御性写作取代正向定义
**问题：** 一段话反复写“我们不声称……”“这并不意味着……”“并非……”，却没有先解释模型是什么。
**改法：** 先正面定义有限维受控 Koopman 近似；仅在可能引起实质数学误解处，用一句话限定。例如不能把有限维矩阵对 `(A,B)` 直接说成无限维算子 `K_u`，但也不需要整段辩护。

### 反例 B：物理状态和测量状态突然切换
**问题：** Koopman 算子先作用于真实状态 `s` 的观测函数，随后提升映射直接写成测量 `x` 的函数，中间没有桥接。
**改法：** 首次切换时说明 `x=h(s)`，基于测量的字典对应复合观测函数 `g_j∘h`；不要把桥接说明散落在多个段落。

### 反例 C：引入只出现一次的新算子
**问题：** 为表达“由历史和未来控制预测未来状态”，额外定义 `\mathcal P_\Theta^{(H)}`，却未解释、后文也不使用。
**改法：** 直接用一句任务定义替代，减少符号负担；若保留，必须首次完整定义并在后文实际复用。

### 反例 D：数学定义里塞入实现细节
**问题：** 定义历史条件化映射 `C_\phi` 时，立即指定 affine–tanh MLP 与向量化拼接，使一般性定义被具体实现打断。
**改法：** 定义段写 `C_\phi:(X,U^{in})\mapsto c\in\mathbb R^{d_c}` 及作用；参数化另行集中说明，保留可复现性。

### 反例 E：预测状态角色未交代
**问题：** `z^E` 与 `z^P` 交替出现，读者不知一个来自编码器、一个来自递推。
**改法：** 在首次并列出现时一句话解释，并在递归公式明确“编码一次、之后传播”，不要在后文重复多次。

### 反例 F：理论性质超出实际证明
**问题：** 把有限时域误差上界或低秩修正的范数约束写成全局稳定性、闭环鲁棒性或递归可行性。
**改法：** 只写已建立的命题及条件；例如 `||A(c)-A_0||_2≤g_max` 本身不保证 `A(c)` 稳定。

### 反例 G：优化器名称与实现不一致
**问题：** 正文写 RTI-QP，代码却可能只是对原始非线性代价进行有限次 quasi-Newton 迭代。
**改法：** 核对实际目标、梯度/Jacobian、约束与求解器后再命名；证据不足时列为待核验，不能靠措辞修补。

### 反例 H：框架图抢在定义之前
**问题：** 大幅双栏图与超长图注出现在模型符号解释之前，图注重复整段方法。
**改法：** 先给关键定义，再以图总结；图注解释图的结构，不重写正文。注意 LaTeX `figure*` 的实际位置需编译检查。

## 五、可执行的论文精修工作流（未来 Skill 的核心）

### 阶段 0：读取与锁定范围
1. 读取用户指定版本、意见、相关章节、符号定义、公式引用、项目写作规则；如有代码一致性问题，再读取相关实现。
2. 明确本轮**允许修改的章节/段落**、禁止触碰的章节（尤其未授权的实验）、要保留的公式标签和接口。
3. 检查版本与差异，避免把旧版意见误用到新版。

### 阶段 1：诊断，不急着重写
对每个问题标记类别：
- `LOGIC` 论证断裂或任务不明确
- `ROLE` 章节职责越界
- `SYMBOL` 符号未定义、重复定义、维度不一致
- `MATH` 数学错误或条件缺失
- `CLAIM` 主张超过证据
- `IMPLEMENTATION` 与代码不符或不可复现
- `STYLE` 重复、空话、防御性解释、过长句
- `LAYOUT` 图表位置、图注、浮动体与交叉引用

### 阶段 2：确定最小修复动作
优先级依次为：
1. 数学错误、实现不一致、证据越界；
2. 符号定义缺失、论证链断裂、章节越界；
3. 重复与冗长、句式和排版。

每个问题只选必要动作：`保留 / 删除 / 压缩 / 前移 / 后移 / 替换 / 待核验`。不要默认“重写整节”。

### 阶段 3：精修执行
- 保留原文中已正确的内容；优先局部替换。
- 数学公式和引用标签默认不变；确需删除时检查全文引用。
- 对首次出现的变量提供最短完整定义；后续直接使用。
- 方法细节与理论一般性分层写；不删除必要的复现信息。
- 图注精简，图表与正文互补而非重复。
- 任何实验数值、文献、代码行为都不得凭空补充。

### 阶段 4：复核
- **局部复核：** 改后段落能否独立读懂？变量、维度、公式顺序是否成立？
- **全局复核：** 前后章节术语、符号、贡献与实验是否一致？
- **技术复核：** 公式标签/引用、LaTeX 编译（如环境允许）、代码对照（如有代码）。
- **诚实报告：** 明确“已检查”“未检查”“受环境限制”，不虚构编译或实现验证。

### 阶段 5：交付
输出至少包含：
1. 本轮修改范围与禁区；
2. 按严重度排序的问题表（位置、原文、问题、理由、处理动作）；
3. 可直接复制的英文 LaTeX 替换稿（仅限需改部分）；
4. 修改前后逻辑与跨章节影响；
5. 待核验事项与验收清单。

## 六、句子级写作检查：四问法

对每句话问：
1. **信息：** 这句话提供了新的定义、因果、条件、证据或过渡吗？
2. **位置：** 这句话应该出现在当前章节吗？
3. **准确：** 主语、对象、限定条件、数学含义和证据是否匹配？
4. **必要：** 删除后会丢失理解所必需的信息吗？若不会，删除或合并。

对每个公式问：**为什么现在需要？变量是否定义？维度是否匹配？后文是否使用？**

对每个段落问：**读者读完能回答哪个明确问题？**

### 未来 Skill 的入口指令草案

> 当用户请求撰写、审阅或精修学术论文时，先读取论文原文、用户意见和写作规范，识别论文类型及本轮允许修改范围。先审查论证、数学定义、符号、证据边界与章节职责，再处理语言风格。坚持问题驱动、正向定义、信息密度和最小修改；不得增加未验证的实验结果、虚构引用、改变未经授权的章节，或将有限时域性质夸大为全局保证。输出定位准确的问题清单、最小修改方案、必要的 LaTeX 替换稿与未核验事项。修改后检查符号一致性、引用完整性及可用的编译/代码证据。

## 八、不要写成 Skill 硬规则的经验性数字

公众号文章中的“四段引言”“五句话摘要”“讨论四步”“三句结论”“拆两百篇”等，是作者个人总结的**启发式经验**，并非学术期刊的统一规定。未来 Skill 应把它们写成“可选结构模板”，而非强制字数、段落数或句子数。不同领域、期刊、论文类型以及是否单设 Discussion 都可能不同。

## 九、最终验收清单

- [ ] 论文的核心问题能用一到两句话准确陈述
- [ ] 每个核心模块对应一个真实问题，而不是为模块编造需求
- [ ] 各章节只承担自己的主要职责
- [ ] 关键变量、符号、维度、上标和缩写首次出现即定义
- [ ] 数学对象的关系准确（例如算子与有限维近似不混同）
- [ ] 训练、推理、控制流程和代码行为没有被混写
- [ ] 理论结论与假设、适用范围严格对应
- [ ] 实验主张有可追溯的证据；未验证数据不进入摘要与结论
- [ ] 每幅图、每个公式都有明确作用，图注不复述整节
- [ ] 没有多余的防御性解释、空泛套话与重复动机
- [ ] 未修改用户未授权的章节或内容
- [ ] 已报告编译、交叉引用、代码对照的实际验证状态

---

**一句话原则：** 不追求“写得像顶刊”，而是让读者用最小认知成本，准确理解一个有证据支撑、数学自洽、可以复核的研究贡献。
